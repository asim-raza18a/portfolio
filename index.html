Integration guideSecurity
Read +
Brief. Explain the authorization code flow with PKCE to developers who have implemented OAuth before but not against this platform. Avoid re-teaching OAuth; focus on what is specific here.

Authenticating with the Meridian API

Meridian uses the OAuth 2.0 authorization code flow with PKCE. If you have implemented OAuth elsewhere, three things differ here and they account for most failed integrations.

1. Scopes are additive and cannot be widened on refresh

A refresh token inherits the scopes granted at authorization. Requesting a broader scope on refresh returns invalid_scope; you must send the user back through the consent screen. Request everything you need up front, even features you plan to ship later.

2. The redirect URI must match exactly, including the trailing slash

https://app.example.com/callback and https://app.example.com/callback/ are different URIs. Register both if you are unsure which your framework emits.

3. Tokens are bound to an organisation, not a user

A user who belongs to three organisations produces three distinct tokens. Store them keyed on (user_id, org_id). Storing one token per user is the most common cause of "works for me, fails for the customer" reports.

Exchange request
POST /oauth/token
grant_type=authorization_code
&code=AUTH_CODE
&code_verifier=VERIFIER
&client_id=CLIENT_ID
&redirect_uri=https://app.example.com/callback
Access tokens live for 60 minutes. Refresh tokens rotate on every use. Store the new refresh token from each response or the next refresh will fail with invalid_grant.
DemonstratesRespecting what the reader already knows. The guide refuses to re-explain OAuth and spends its length on the three platform-specific behaviours that break integrations, which is what a developer with prior OAuth experience actually needs.

Quickstart: first successful call in under five minutes

Getting startedDeveloper onboarding
Read +
Brief. The platform's existing quickstart took 40 minutes and lost most developers at the environment setup step. Rewrite so a developer reaches a working response as fast as possible, with configuration deferred until after the first win.

Quickstart

This gets you a working API response. It does not get you a production integration. That is the next guide. Nothing here needs a local environment.

1. Get a sandbox key

Sandbox keys are issued instantly and need no billing details. They are prefixed sk_sandbox_ and are rejected by production endpoints, so you cannot accidentally charge anyone.

2. Make a call
curl https://api.meridian.dev/v1/accounts \
  -H "Authorization: Bearer sk_sandbox_YOUR_KEY"

You should get a single seeded demo account:

{ "data": [ { "id": "acct_demo", "name": "Demo Account", "status": "active" } ] }

If you got 401, the key has a trailing space. That is the most common cause by a wide margin. If you got an empty array, your sandbox has not finished seeding; wait ten seconds and retry.

3. Change something
curl -X PATCH https://api.meridian.dev/v1/accounts/acct_demo \
  -H "Authorization: Bearer sk_sandbox_YOUR_KEY" \
  -d '{"name":"My first change"}'

That is the whole pattern. Every resource in the API follows the same shape: list with GET, modify with PATCH, and nothing is destructive without an explicit DELETE.

Next: Moving to production covers key rotation, webhooks and the idempotency model. Read it before you ship, not before you experiment.

DemonstratesOnboarding sequenced around momentum. Setup is deferred, the two most frequent failure causes are pre-empted inline, and the final line tells the reader what to skip for now. Reducing the cognitive load that makes developers abandon quickstarts.

SDK installation and configuration, Python

Brief. Installation page for a Python SDK. Must cover virtual environments without patronising experienced developers, and must address the dependency conflict the support team sees weekly.

Installing the Python SDK

pip install meridian-sdk

Requires Python 3.9 or later. The SDK pins httpx>=0.24; if your project pins an older httpx, installation will resolve but requests will fail at runtime with a TypeError on timeout. Check with pip show httpx before filing a bug.

Configuration

The client reads MERIDIAN_API_KEY from the environment by default:

from meridian import Client

client = Client()                      # reads env var
client = Client(api_key="sk_live_...") # or pass explicitly
Timeouts and retries

The default timeout is 10 seconds with three retries on 429 and 5xx, using exponential backoff. Retries are not applied to POST requests unless you supply an idempotency key. The SDK will not risk duplicating a write on your behalf.

client = Client(timeout=30, max_retries=5)
Async

An async client is available with identical method signatures:

from meridian import AsyncClient

async with AsyncClient() as client:
    accounts = await client.accounts.list()
Do not instantiate a new Client per request. It opens a fresh connection pool each time. Create one at application startup and reuse it.
DemonstratesInstallation docs that encode support knowledge. The httpx conflict, the no-retry-on-POST decision and the connection-pool warning are the things that cost users hours, each stated where the reader will hit it.

Webhooks: delivery, verification and replay

Integration guideEvent-driven
Read +
Brief. Developers were building webhook consumers that broke under retries and duplicate deliveries. Document the delivery guarantees honestly, including what the platform does not promise.

Receiving webhooks

What we guarantee, and what we don't

Delivery is at least once. You will sometimes receive the same event twice. Ordering is not guaranteed, a shipment.delivered event can arrive before shipment.dispatched for the same shipment. Build your consumer to tolerate both.

Every event carries a stable id and a monotonic sequence per resource. Discard any event whose sequence is lower than the one you have already processed for that resource. This is the whole of correct consumption.

Verifying the signature
import hmac, hashlib

def verify(payload: bytes, header: str, secret: str) -> bool:
    ts, sig = header.split(",")
    expected = hmac.new(
        secret.encode(),
        f"{ts}.".encode() + payload,
        hashlib.sha256
    ).hexdigest()
    return hmac.compare_digest(expected, sig)

Use compare_digest, not ==. Reject any request whose timestamp is more than five minutes old to prevent replay.

Retry schedule
AttemptDelay
1–310s, 30s, 2m
4–610m, 1h, 6h
724h, then the endpoint is disabled

Return 2xx quickly and process asynchronously. Any response taking longer than 10 seconds counts as a failure, even if you eventually return 200.

DemonstratesStating negative guarantees plainly. Most webhook docs describe the mechanism; this one leads with what the platform does not promise, because that is what determines whether the consumer is written correctly.

Migrating from v1 to v2

Budget: a typical integration takes two to four engineering days. If you use bulk exports or the legacy /search endpoint, add two more. v1 is accepted until 31 March 2027; after that it returns 410 Gone.

RAG pipeline, architecture overview for implementers

★ Start hereArchitectureRAG
Read +
Brief. Engineers deploying a retrieval-augmented generation platform need to understand the pipeline well enough to debug it. Explain each stage, what it can get wrong, and which knob affects which failure.

How retrieval works

A query passes through five stages before a response is generated. Most quality complaints trace to one specific stage, and knowing which saves a great deal of guesswork.

1. Chunking (ingestion time)

Documents are split into passages of roughly 500 tokens with 80 tokens of overlap. Overlap exists so a fact spanning a boundary survives in at least one chunk intact.

Fails when: source documents are tables or deeply nested structures. A table split across chunks produces rows without headers, which retrieve confidently and answer wrongly. Set chunk_strategy: "structural" for table-heavy corpora.

2. Embedding

Each chunk becomes a vector. Embeddings are model-specific: if you change the embedding model you must re-index the entire corpus. Mixed-model indexes return nonsense rather than erroring, which makes this failure slow to spot.

3. Retrieval

The query is embedded and the top_k nearest chunks are returned (default 8). Hybrid search runs this alongside BM25 keyword matching and merges by reciprocal rank fusion.

Fails when: the query uses vocabulary absent from the corpus. Product codes, internal acronyms, surnames. Pure vector search handles these badly. Hybrid search exists almost entirely for this case.

4. Reranking

A cross-encoder rescores the retrieved chunks and keeps the best top_n (default 3). This is slower than retrieval but much more accurate, which is why we over-retrieve at stage 3 and discard here.

5. Generation

Surviving chunks are placed in the prompt with their source references. The model is instructed to answer only from supplied context and to state when the context is insufficient.

Fails when: retrieval returned plausible-but-wrong chunks. The model has no way to know the context is wrong, so it answers fluently and incorrectly. Generation quality problems are usually retrieval problems.

Diagnosing by symptom
SymptomLook at
Answers are confident and wrongRetrieval. Inspect the chunks actually passed to the model before touching the prompt.
Answers miss facts you know are in the corpusChunking, then top_k. Check whether the fact survived ingestion intact.
Exact identifiers never matchHybrid search is off.
Quality dropped after a model changeStale index. Re-embed.

LLM observability, instrumenting a production pipeline

★ Start hereObservabilityOperations
Read +
Brief. Teams ship LLM features with no visibility and discover quality regressions from customer complaints. Document what to trace, what to measure and what the numbers mean.

Instrumenting an LLM application

Conventional APM tells you a request took 2.4 seconds and returned 200. For an LLM feature that is nearly useless, the request can succeed, perform well, and still be wrong. You need traces that capture the content, not just the timing.

The trace shape

One user interaction is one trace. Inside it, record a span per pipeline stage:

trace: conversation_turn
├── span: retrieval        (query, top_k, chunk_ids, scores)
├── span: rerank           (input_ids, output_ids, scores)
├── span: generation       (prompt_tokens, completion_tokens, model, temperature)
└── span: post_process     (filters applied, citations resolved)

Record chunk IDs and scores, not chunk text. Text makes traces enormous and creates a second copy of your corpus in a system with different access controls.

What to measure
MetricWhy it mattersInvestigate when
Retrieval score distributionFalling top-1 scores mean queries are drifting away from the corpusMedian top-1 drops more than 15% week on week
Context utilisationShare of retrieved chunks actually cited in the answerBelow 40%. You are retrieving noise and paying for it
Refusal rateHow often the model says it cannot answerSudden rise usually means an ingestion job failed
Token cost per resolved queryThe only cost metric tied to valueRising while resolution stays flat
Time to first tokenWhat users actually perceive as speedp95 above 1.2s
Sample your traces, keep your failures. Full-fidelity tracing on every request is expensive. Sample 5% of successful turns, but retain 100% of turns where the user gave negative feedback, retried, or abandoned. Your failures are the dataset worth having.
Redaction

Prompts contain user input and user input contains personal data. Configure redaction at the SDK layer, before the trace is emitted, not in the observability platform, where the raw payload has already crossed a network boundary.

Brief. A team wants to choose between three models for a support-automation feature. Write the methodology document that makes the comparison defensible to a sceptical stakeholder.

Evaluation methodology, support response generation

What we are measuring

Not "which model is best". The question is: which model resolves the most support conversations without escalation, at acceptable cost, without producing an answer that would embarrass us. Those are three separate criteria with different tolerances, and a model can win on two and still be disqualified by the third.

Dataset

400 historical conversations sampled stratified across issue category, with resolution outcome known. Deliberately includes 60 conversations that escalated to a human, a model that confidently answers the unanswerable is worse than one that escalates.

Conversations are held out from any fine-tuning corpus. Where an agent's reply is the reference answer, it has been reviewed; roughly 8% of historical replies were themselves wrong and have been corrected or excluded.

Scoring
DimensionMethodThreshold
Factual accuracyHuman review, 2 raters, disagreements adjudicated by a third≥ 95%; this is a gate, not a score
ResolutionWould this reply have closed the ticket? Human judgementCompare to the 71% human baseline
Appropriate escalationRecall on the 60 known-escalation cases≥ 90%
ToneLLM-as-judge against a rubric, 10% human-auditedDirectional only, not a deciding metric

Stated limitations
  • 400 conversations gives roughly ±5 percentage points at 95% confidence. Differences smaller than that are not real differences.
  • Historical conversations predate the current product version; some reference deprecated features.
  • LLM-as-judge correlates with human raters at about 0.7 on tone. We use it to flag outliers, not to rank.
  • Cost uses list pricing and ignores negotiated rates and caching discounts.

Decision 1, index type
TypeUse whenTrade-off

hnsw100k–50M vectorsApproximate. Fast queries, slow builds, high memory. The default choice at scale.

Decision 2, HNSW parameters

  • ef_construction (default 200), effort at build time. Higher builds slower but produces a better graph. This is a one-off cost; 400 is usually worth it.

Decision 3, filtering strategy

Metadata filters can be applied before or after the vector search. Pre-filtering is exact but can be slow on low-selectivity filters; post-filtering is fast but may return fewer than top_k results, sometimes zero.

Rule of thumb: if your filter excludes more than 90% of the corpus, pre-filter. Otherwise post-filter and over-retrieve by 3×.
Measure recall before optimising latency. An index that answers in 5ms with 70% recall is worse than one answering in 40ms with 98%. Users notice wrong answers; they do not notice 35 milliseconds.

User guidePrompting

Brief. Non-technical operations staff configure prompts for automated workflows. Teach the few techniques that reliably help, without folklore.

Writing prompts that behave consistently

You are writing instructions that will run thousands of times on inputs you have not seen. That is a different job from chatting with an assistant, and the techniques differ.

Put the task before the data

Models attend most reliably to the beginning and end of a prompt. State the task first, supply the data, then restate the output format last.

Classify this support ticket into one of: billing, technical, account, other.

TICKET:
{{ticket_text}}

Reply with only the category name, lowercase.
Define the edge case, or the model will invent one

"Classify into billing, technical, account, other" leaves the model to decide what happens with an empty ticket, a ticket in Spanish, or one that is clearly spam. Say it:

If the ticket is empty, unintelligible, or spam, reply: other

Unspecified cases are where production behaviour drifts, because the model's choice is not stable across versions.

Show two examples, not ten

Two or three well-chosen examples, including one near-miss, outperform ten similar ones. Pick the cases your team argues about, not the obvious ones.

Constrain the output shape

"Reply with only the category name" removes the preamble. Where the output feeds another system, specify JSON and give the exact keys. Models follow format instructions far more reliably than tone instructions.

What does not work
  • Shouting. "VERY IMPORTANT!!!" does not outrank a clear instruction.
  • Threats and rewards. Offering a tip or claiming someone's job depends on it is folklore. It does not survive testing.
  • Piling on adjectives. "Act as a world-class expert" adds length, not accuracy. Describe the task precisely instead.
Change one thing at a time and keep a record. Prompt changes interact. Teams that edit three things and ship the result cannot explain their own quality regressions a month later.
DemonstratesTeaching a non-technical audience without condescension, and explicitly debunking widespread folklore, which is what separates a useful prompting guide from the many that repeat received wisdom.

★ Start hereTechnical blogThought leadership
Read +
Brief. A developer-tools company needs blog content that ranks and earns respect from engineers. No product pitch until the final paragraph, and the technical substance has to be correct enough to survive a Hacker News comment thread.

Why your RAG system is confidently wrong

A retrieval system that returns the wrong passage doesn't fail loudly. It hands a plausible chunk to a language model, the model does exactly what you asked, answer from the provided context, and you get a fluent, well-cited, incorrect answer. The citation makes it worse, because it looks like evidence.

Teams respond by rewriting the prompt. That almost never helps, because the prompt is not where the failure happened.

The failure is upstream

Consider a policy corpus where one document says contractors are ineligible for the travel allowance, and a second, newer document says contractors on assignments over six months are eligible. A user asks: "Can contractors claim travel?"

Both chunks are semantically near the query. Both are retrieved. The reranker has no notion of recency, so it orders them by relevance, and the older, more direct statement wins because it matches the question more tightly. The model answers "No", grounded, cited, and wrong.

No amount of prompt engineering fixes this. The correct information never reached the model.

Three fixes, in order of how much they'll help

1. Put metadata in the index and use it. Effective dates, document status, supersession. A chunk from a superseded policy should be filtered out before ranking, not out-argued afterwards. This is unglamorous and it resolves the largest share of contradiction failures.

2. Retrieve more, then rerank harder. Pulling top_k=8 and reranking to 3 beats pulling top_k=3 directly, because the cross-encoder sees competing passages and can discriminate between them. The cost is one extra model call on a short list.

3. Let the model say the context disagrees. Most prompts instruct the model to answer from context. Few permit it to report that the context contains a conflict. Adding that option converts a silent wrong answer into a visible flag, and a flagged conflict is a corpus bug you can fix.

What to measure

Answer accuracy tells you that something is wrong but not where. Measure retrieval separately: for a set of questions with known source passages, what proportion of the time is the correct passage in the retrieved set at all? If that number is 70%, your ceiling is 70% no matter what the model does, and every hour spent on the prompt is an hour spent on the wrong layer.

Most teams have never measured it. It is usually lower than they expect, and it is almost always the cheapest thing to improve.

We built retrieval tracing into Meridian because we kept watching teams debug the generation step for a problem three stages upstream. If you want to see which chunks your model actually received, that's what it's for.

Governing AI systems in regulated industries

Executive summary

Financial services and healthcare organisations are deploying AI systems faster than their governance functions can assess them. The common response, extending existing model risk management frameworks, is partially correct and insufficient, because those frameworks assume a model whose behaviour is stable between validations. Language models are not stable in that sense: the same system can change behaviour through a vendor update, a prompt change, or a shift in retrieved context, none of which triggers a conventional model change control.

This paper argues that AI governance in regulated settings needs three additions to existing frameworks, and that organisations attempting to govern AI purely through pre-deployment validation will be surprised.

Second, the unit of governance is the system, not the model. Retrieval configuration, prompt templates and post-processing filters change outputs as much as model weights. Treating the weights as the governed artefact leaves most of the behaviour ungoverned, and in practice most incidents originate outside the model.

"A human reviews the output" is not a control unless you have defined what the reviewer checks, what proportion they see, how fatigue is managed, and how often they overturn the system. Unmeasured human oversight tends toward rubber-stamping, and an unmeasured control is not a control.

These are additions, not replacements. Existing model risk discipline, documented purpose, bounded use, named accountable owner, remains necessary. The argument here is that it stops short of sufficient.

2.3 Evaluating retrieval in generative systems

Evaluation of retrieval-augmented systems has largely inherited its measures from classical information retrieval, where relevance is judged against a query. This inheritance is convenient and increasingly contested, because the consumer of retrieved material in a generative system is not a human reader but a language model with different sensitivities.

The classical measures, precision, recall and normalised discounted cumulative gain, assume that a user inspects a ranked list and that position matters in proportion to attention. Neither assumption holds cleanly. A generative system typically consumes a small set of passages without regard to their ordering, so ranking metrics measure a property that the downstream consumer largely ignores. Several authors have accordingly argued for set-based rather than rank-based evaluation at the retrieval stage, while retaining ranking measures where a reranker is present.

A second and less resolved difficulty concerns sufficiency. Classical recall asks whether relevant documents were returned; it does not ask whether the returned set is sufficient to answer the question. A retrieval set may contain every individually relevant passage while omitting the connecting fact that makes an answer derivable. Work on multi-hop question answering has surfaced this problem most clearly, and proposals for "answer-bearing" or "supporting-set" metrics attempt to address it, though no measure has achieved general adoption.

A third strand questions whether retrieval should be evaluated in isolation at all. End-to-end evaluation against answer correctness has the virtue of measuring what is actually wanted, but conflates retrieval and generation failures in a way that provides no diagnostic signal, the practical objection being that a team told only that accuracy is 62% cannot act on it. The emerging compromise is paired evaluation: an end-to-end measure for tracking, and a component-level retrieval measure for diagnosis.

Gap

What remains underexplored is evaluation under corpus contradiction. The literature predominantly assumes a corpus in which relevant passages are mutually consistent, so that retrieving any sufficient subset yields a correct answer. Operational corpora routinely violate this: policy documents supersede one another, versioned documentation describes incompatible behaviours, and both versions remain indexed. Under contradiction, a retrieval set can score perfectly on every measure discussed above and still produce a confidently incorrect answer, because correctness depends on which of two relevant passages the generator privileges.

This dissertation addresses that gap by proposing a contradiction-aware retrieval measure and evaluating it against a corpus with annotated supersession relationships.

DemonstratesLiterature review that argues rather than lists. Each paragraph advances a line of critique toward the gap, the three strands are related to one another rather than summarised in sequence, and the identified gap is specific enough to be researchable, which is the difference between a review that justifies a dissertation and one that merely precedes it.

4. Findings, order fulfilment review

4.1 The stated problem is not the actual problem

We were engaged to reduce picking times in the Birmingham facility, which management identified as the constraint on same-day dispatch. Picking is not the constraint.

Timing across 1,240 observed orders places median pick at 6.4 minutes against an industry benchmark of 5–8 minutes for comparable SKU density. The facility is performing normally at this step. The delay sits earlier: median time from order receipt to pick-list release is 94 minutes, of which 71 is spent in a credit-check queue that runs in scheduled batches four times a day rather than continuously.

An order arriving at 09:05 waits until the 11:00 batch before picking can begin. Compressing pick time by a minute changes nothing for that order.

4.2 The batch schedule has no current justification

Four-times-daily batching was introduced in 2019 when credit checks were performed manually by a two-person team. That process was automated in 2023; the schedule was not revisited. The automated check completes in under four seconds and the system supports continuous operation. No one we interviewed could state a reason for the current schedule, and three assumed it was a system limitation.

4.3 Consequences of the misdiagnosis

£340,000 of the proposed capital budget is allocated to picking automation addressing a step that is not the bottleneck. On our timings, the projected 18% improvement in that step would reduce end-to-end fulfilment time by approximately 4%, against a stated target of 35%.

Moving credit checks to continuous operation is a configuration change. It requires no capital and would reduce median order-to-dispatch time by an estimated 60–65% on its own.

This is not an oversight by the operations team, and we want to be clear about that. Performance is reported by department, and each department's metrics look healthy: credit control reports a four-second check time, warehouse reports a 6.4-minute pick. The 71-minute queue sits between two departments and appears in neither report. The measurement system has no owner for the gaps between functions, which is the finding with the widest application beyond this engagement.
