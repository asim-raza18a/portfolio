Section 1Scope

This document specifies how to instrument an LLM or agent workload so that its behaviour is observable in production. It covers trace structure, attribute conformance, metric definitions, sampling policy, cardinality control and backend selection.

In scope

  • Span taxonomy and naming for inference, retrieval, tool execution and agent orchestration.
  • Attribute requirements under the OpenTelemetry GenAI semantic conventions, including which attributes are stable and which are not.
  • Metric instruments, their units and dimensions.
  • Content capture policy and the privacy boundary.
  • Sampling design, with the arithmetic for choosing rates.
  • Cardinality budgeting and storage sizing.
  • Backend selection criteria and migration cost.

Out of scope

  • Model quality evaluation methodology. Evaluation is covered only where it emits or consumes telemetry.
  • Infrastructure monitoring of inference servers. Standard practice applies.
  • Prompt engineering, model selection and retrieval design.

Conventions used

Requirement keywords follow RFC 2119. MUST indicates a requirement for conformance with the referenced specification. SHOULD indicates a strong recommendation with legitimate exceptions. MAY indicates an option. Where this document makes a recommendation beyond the specification, it is marked as such.

TermDefinition
TraceOne end-to-end user interaction, from request receipt to response completion.
SpanOne timed unit of work within a trace, with attributes and a parent.
ObservationPlatform-specific term, used by some backends in place of span. Treated as synonymous here.

ScoreA numeric or categorical judgement attached to a trace or span after the fact.

Section 2Why conventional APM is insufficient

Standard application performance monitoring answers whether a request completed and how long it took. For an LLM workload those two facts have weak correlation with whether the system did its job.

The failure classes APM cannot see

FailureHTTP statusLatencyAPM verdictReality
Model hallucinated a fact200NormalHealthyUser given wrong information
Retrieval returned nothing relevant200NormalHealthyAnswer generated from noise
Reranker timed out, served unranked200Slightly fasterImprovedQuality degraded silently
Prompt template regression dropped a constraint200NormalHealthyPolicy violations in output
Context truncated at the token limit200NormalHealthyAnswer missing the decisive source
Agent looped three extra times2003x normalSlow endpointCost 3x, correct diagnosis requires span-level detail

In five of the six rows, every signal available to conventional APM is nominal. The sixth is visible as latency but not diagnosable without per-step detail.

What the telemetry must therefore carry

  1. Structure. A span per pipeline stage, so a quality problem can be localised to a stage rather than attributed to the whole request.
  2. Inputs and outputs, selectively. Identifiers and scores always; raw content under policy. Without some view of what entered the model, a wrong answer is not debuggable.
  3. Semantic attributes. Token counts, model identity, temperature, finish reason. These are the dimensions every useful aggregate is grouped by.
  4. Post-hoc scores. Quality is determined after the request completes, by a judge, a human, or user behaviour. The telemetry model must accept writes to a trace after it has closed.

That last requirement is the one that distinguishes LLM observability from tracing generally, and it is why several purpose-built platforms exist alongside general OTel backends.

Section 3Convention status

Implementers consistently overestimate the maturity of the GenAI conventions. The current status affects how you should version your instrumentation and how much churn to plan for.

Current state

As of mid-2026, every gen_ai.* attribute, span, metric and event in the OpenTelemetry registry carries the stability badge Development, the status formerly called experimental. None is marked Stable. Published claims that the conventions "went stable" in some earlier release are not supported by the registry.

Stability progresses through three levels: Development, Release Candidate, Stable. The GenAI conventions sit at the first.

The only Stable attributes appearing on a conforming GenAI span are inherited from the core conventions rather than authored by the GenAI group:

AttributeStatusOrigin
error.typeStableCore conventions
server.addressStableCore conventions
server.portStableCore conventions
Everything with a gen_ai. prefixDevelopmentGenAI conventions

The June 2026 repository split

On 12 June 2026, with semantic-conventions v1.42.0, the GenAI conventions moved out of the core semantic-conventions repository into a dedicated repository, open-telemetry/semantic-conventions-genai. That repository now holds the GenAI spans, metrics and events, the MCP conventions and provider-specific conventions such as the OpenAI ones.

Practical consequence: documentation, issue tracking and release cadence for GenAI conventions are now decoupled from the core. Pinning to a core semconv version no longer pins your GenAI attribute definitions.

Transition guidance for existing instrumentation

The specification instructs instrumentations emitting v1.36.0 conventions or earlier that they SHOULD NOT change the version they emit by default, and SHOULD introduce an environment variable allowing operators to opt into a newer version. Conventions in scope include attributes, metric names, span names, event names, span kind and units of measure.

Implication for your rollout. Treat the convention version as a deployment variable, not a library detail. An SDK upgrade that silently changes attribute names breaks every dashboard and alert built on them. Pin the convention version explicitly and change it deliberately, with the dashboard migration planned in the same change.

Recommended posture

  1. Emit the conventions, because the alternative is a bespoke schema that no backend understands.
  2. Pin the convention version in configuration and record it as a resource attribute, so you can tell which traces used which schema.
  3. Isolate attribute names behind constants in one module. When a name changes, you edit one file.
  4. Expect breaking changes at least annually until the conventions reach Release Candidate.

Section 4Span taxonomy

The conventions define span types for inference, agent lifecycle and framework operations. Correct naming and kind matter because backends group and visualise on them.

Naming

For inference spans, the span name SHOULD be {gen_ai.operation.name} {gen_ai.request.model}. For example chat gpt-4 or embeddings text-embedding-3-large. Individual GenAI systems and frameworks MAY specify a different format but MUST follow the general guidelines for span names, which require low cardinality.

Low cardinality is a requirement, not a suggestion. Interpolating a user ID, a session ID or the prompt text into a span name produces unbounded distinct names. Most backends index on span name, and unbounded names degrade query performance and inflate storage. Put high-cardinality values in attributes, where they belong.

Span kind

Inference span kind SHOULD be CLIENT, because the application is calling an external service, and MAY be INTERNAL for spans representing operations that do not cross a process boundary, such as a locally hosted model.

Span status

Status SHOULD follow the core Recording Errors guidance. In practice: set status to error only for failures, record error.type, and do not set error status for a model refusal or a low-quality answer. A refusal is a successful operation with an unwanted outcome, and conflating the two makes your error rate meaningless.

Operation types

OperationRepresentsTypical kind

text_completionA non-chat completionCLIENT
embeddingsAn embedding requestCLIENT
create_agentAgent instantiationCLIENT or INTERNAL
invoke_agentOne agent executionCLIENT or INTERNAL
execute_toolOne tool call made by an agentINTERNAL, or CLIENT if it calls out

Provider discrimination

The gen_ai.provider.name attribute acts as a discriminator identifying which provider-specific telemetry flavour applies within the GenAI conventions. It SHOULD be set consistently with provider-specific attributes and signals, and for OpenAI operations it MUST be "openai". Other registry examples include gcp.gen_ai and gcp.vertex_ai.

Provider-specific conventions extend and override the general GenAI conventions. If you call more than one provider, expect attribute sets to differ between providers for semantically similar concepts, and normalise in your queries rather than assuming uniformity.

Creation-time attributes

Certain attributes are important for sampling decisions and SHOULD be provided at span creation time rather than set later. gen_ai.provider.name is explicitly called out for OpenAI spans, and the agent conventions name gen_ai.agent.name among others.

The reason is mechanical: a head sampler decides whether to record a span when it starts. An attribute set after creation cannot influence that decision, so a sampling rule that keys on it will not work.

Request parameter attributes

The registry defines attributes for the sampling parameters sent with a request, including gen_ai.request.temperature, gen_ai.request.top_p, gen_ai.request.max_tokens, gen_ai.request.frequency_penalty, gen_ai.request.presence_penalty, gen_ai.request.stop_sequences, gen_ai.request.seed, gen_ai.request.choice.count and gen_ai.request.stream.

Section 6Standard metrics

The conventions define two client instruments. Both are low cardinality by design and should be emitted regardless of sampling policy, because metrics and traces answer different questions.

The two instruments

MetricInstrumentUnitPurpose
gen_ai.client.token.usageHistogram{token}Token consumption per operation, split by input and output
gen_ai.client.operation.durationHistogramsWall-clock duration of the client operation

Why histograms rather than counters

A counter of total tokens tells you the bill. A histogram tells you the distribution, which is what you need to detect a change in behaviour. A median that is flat while p99 doubles indicates a new class of request, and a counter cannot show that.

Bucket boundaries matter. Default boundaries are tuned for HTTP latencies in milliseconds and are a poor fit for generation durations measured in seconds, or token counts in the thousands. Configure explicit boundaries.

from opentelemetry.sdk.metrics.view import View, ExplicitBucketHistogramAggregation

views = [
    View(
        instrument_name="gen_ai.client.operation.duration",
        aggregation=ExplicitBucketHistogramAggregation(
            boundaries=[0.1, 0.25, 0.5, 1, 2, 4, 8, 16, 32, 64]
        ),
    ),
    View(
        instrument_name="gen_ai.client.token.usage",
        aggregation=ExplicitBucketHistogramAggregation(
            boundaries=[64, 256, 1024, 2048, 4096, 8192, 16384, 32768, 131072]
        ),
    ),
]

Dimensions

Both instruments should carry the low-cardinality subset of the span attributes: operation name, provider, request model, response model, error type. Do not add tenant ID, conversation ID or user ID as metric dimensions. Section 11 explains the arithmetic.

Metrics this document recommends adding

The standard instruments cover cost and latency. They do not cover quality or pipeline health. The following are application-defined and worth emitting from the start.

MetricTypeWhy
app.gen_ai.time_to_first_tokenHistogram, secondsFor streaming responses this is the perceived latency. Total duration is not.
app.rag.context_utilisationHistogram, ratioShare of supplied context actually cited. Drives context-length cost decisions.
app.rag.retrieval_top_scoreHistogramDistribution drift indicates queries moving away from corpus coverage.
app.gen_ai.degradedCounterResponses served with a component skipped or timed out.
app.gen_ai.refusalsCounterSplit by reason: insufficient context, policy, below threshold.
app.gen_ai.truncationsCounterContext truncated before the call. A silent correctness risk.
app.agent.stepsHistogramSteps per agent run. A rising tail is runaway cost.

Section 7Content capture

Whether to record prompts and completions is the single highest-consequence configuration decision in LLM observability. It determines both your debugging capability and your compliance exposure.

The specification position

Message content is opt-in. The environment variable OTEL_INSTRUMENTATION_GENAI_CAPTURE_MESSAGE_CONTENT controls whether instrumentations attach gen_ai.input.messages, gen_ai.output.messages and gen_ai.system_instructions. When it is off, which is the default, those attributes are absent entirely.

The default is correct. An instrumentation library that captured user content by default would create a compliance incident on every install.

The trade-off, stated plainly

Content capturedContent omitted
Debugging a wrong answerPossible. You can see what the model was given.Largely impossible. You can see that something went wrong, not what.
Offline evaluation from production trafficPossibleNot possible
Prompt regression analysisPossibleNot possible
Storage costOne to two orders of magnitude higher. See Section 12.Low
Data subject access and erasure scopeIncludes the telemetry storeExcludes it
Blast radius of a telemetry breachUser conversationsMetadata only

Recommended policy

A binary on-or-off decision is usually wrong. A tiered policy gives most of the debugging value at a fraction of the exposure.

TierCaptureApplies toRetention
0No content. Attributes, token counts, scores and IDs only.Default for all traffic90 days
1Content with automated redaction of detected identifiersSampled 1 to 5%, plus all error traces30 days
2Full content, unredactedExplicit opt-in environments only: internal staging, consented beta cohorts7 days
Redaction must happen before the span is exported. Redacting in the observability backend means the raw payload has already crossed a network boundary and been written to a store with different access controls. Implement redaction as a span processor in your own process.

A redacting span processor

REDACTED_KEYS = {
    "gen_ai.input.messages",
    "gen_ai.output.messages",
    "gen_ai.system_instructions",
}

class ContentPolicyProcessor(SpanProcessor):
    def __init__(self, tier: int, redactor):
        self.tier, self.redactor = tier, redactor

    def on_end(self, span):
        if self.tier == 0:
            for key in REDACTED_KEYS:
                span.attributes.pop(key, None)
            return

        if self.tier == 1:
            for key in REDACTED_KEYS & span.attributes.keys():
                span.attributes[key] = self.redactor.scrub(span.attributes[key])
            span.set_attribute("app.content_redacted", True)

Record which tier produced each span. Without it you cannot tell an empty content field from a redacted one, and that distinction matters during an investigation.

Erasure

If content is captured, the telemetry store is in scope for data subject erasure requests. Design for it before you need it:

  • Record a subject identifier on the trace so that erasure can locate the records. A hashed user ID is sufficient and is itself less sensitive than the raw one.
  • Confirm the backend supports deletion by attribute, not only by time range. Several do not, which forces whole-partition deletion.
  • Set retention short enough that most erasure requests are satisfied by expiry rather than by a deletion job.

Design notes

Chunk IDs, never chunk text. Recording retrieved text duplicates your corpus into the telemetry store, multiplies storage by the retrieval depth, and places document content in a system with different access controls. IDs plus scores are sufficient for diagnosis, because you can join back to the corpus when investigating.

Retrieval spans carry both k and returned. A sparse retriever returning 37 of a requested 50 is a signal. Without both numbers the gap is invisible.

Time to first token is an attribute, not a span. It is a point measurement within the generation span, and modelling it as a child span misrepresents the structure.

Version attributes sit on the root span. Placing them on every child wastes storage and adds nothing, because backends propagate root attributes in queries.

Spans the structure deliberately omits

Do not emit a span per retrieved chunk, per candidate scored by the reranker, or per token. These multiply span count by one to three orders of magnitude for diagnostic value that attributes already carry.

The termination attribute

A run terminating at max_steps looks identical in APM to one terminating at completed. Both return 200. The first is a failure the user experiences as an unhelpful answer, and the rate of it is the primary health metric for an agent.

Alert on the ratio, not the count. A max_steps rate above five percent generally indicates either an under-specified task boundary or a tool that is failing in a way the agent cannot recognise.

Cost control via telemetry

Agent cost is unbounded by construction unless something bounds it. Emit cumulative cost per run as an attribute and enforce a budget in the orchestration loop, recording the termination reason when the budget triggers. A run that stops for budget reasons is a controlled failure; one that does not stop is an incident.

Section 10Sampling

Full-fidelity tracing of every request is affordable at prototype volume and not at production volume. Sampling policy determines both your cost and whether the traces you keep are the ones you need.

Head versus tail

Head samplingTail sampling
Decision pointAt root span creationAfter the trace completes, in a collector
Can key on outcomeNoYes. Error, latency, cost, score.
Cost to produceUnsampled traces are never generatedEvery trace is generated and buffered, then discarded
InfrastructureNone beyond the SDKA stateful collector holding traces until complete
Correctness riskKeeps uninteresting traces, discards interesting onesBuffer overflow under load silently drops traces

For LLM workloads tail sampling is substantially more valuable, because the attribute that determines whether a trace is worth keeping, namely whether the answer was any good, is only known at the end. A head sampler has no access to it.

A tiered policy

The policy below is the recommendation of this document. Rates are a starting point to be calibrated against the arithmetic that follows.

ClassRateRationale
Error, any span status ERROR100%Rare and always diagnostic
Degraded, app.degraded=true100%Quality dropped silently. Low volume.
Negative user feedback100%The highest-value dataset you have
User retried or rephrased within 60s100%Implicit dissatisfaction signal
Refusal50%Needs monitoring; higher volume than errors
Agent terminated at max_steps100%Always a defect worth seeing
Latency above p99100%Bounded at 1% by construction
Cost above a per-request threshold100%Bounded and financially material
Everything else2 to 5%Baseline for aggregate trends

The arithmetic

Choose the baseline rate from the detection requirement, not by intuition. If you need to observe a behaviour occurring in a fraction p of traffic, and you want at least n examples per day, at daily volume V, the required rate is:

rate ≥ n / (p × V)

Worked example. Daily volume 400,000 requests. You want at least 30 examples per day of a behaviour affecting 0.5% of traffic.

rate ≥ 30 / (0.005 × 400,000)
     ≥ 30 / 2,000
     ≥ 0.015            → 1.5%

A 2% baseline satisfies this with margin. Note how weakly the requirement scales: to catch a behaviour affecting 0.05% of traffic at the same confidence you would need 15%, which is an order of magnitude more storage for one behaviour. This is the argument for rule-based retention rather than a higher uniform rate. If you can describe the behaviour as a rule, keep 100% of it and leave the baseline low.

Effective retention rate

Compute what your policy actually retains, because teams routinely underestimate it.

effective = Σ (class_fraction_i × class_rate_i)

A policy described as "2% sampling" retains 10.3% of traces. That is five times the storage the headline number implies, and it is the correct answer, but it should be a known number rather than a surprise on the invoice.

Consistency requirements

Sampling decisions MUST be consistent across a trace. A trace with a sampled root and unsampled children is worse than useless, because it presents a complete-looking trace that is missing stages. Use the W3C trace flags and propagate them, which the SDKs do correctly by default.

Metrics must not be sampled. Emit the standard metric instruments on 100% of requests regardless of trace sampling. Metrics are cheap, aggregate correctly, and are the only accurate source for rates and totals. A dashboard computing error rate from sampled traces will be wrong by the inverse of the sampling rate, and the error will vary by class.

Section 11Cardinality control

Cardinality is the dominant cost driver in metric storage and a common cause of backend instability. LLM workloads invite high-cardinality mistakes because the interesting identifiers are all high cardinality.

The multiplication

A metric's series count is the product of its dimension cardinalities. Adding one dimension multiplies; it does not add.

DimensionsDistinct valuesRunning series count
gen_ai.operation.name44
gen_ai.request.model624
gen_ai.provider.name372
app.feature12864
error.type86,912
app.prompt_version20138,240
+ app.tenant_id2,000276,480,000

The final row is the mistake. Adding tenant ID as a metric dimension takes a manageable 138,000 series to 276 million. For a histogram with ten buckets, multiply again by the bucket count plus sum and count fields. Most backends will either bill accordingly or fall over.

Where each identifier belongs

IdentifierMetric dimensionSpan attributeReason
Operation, model, providerYesYesBounded and small
Feature, pipeline versionYesYesBounded. Prune old versions.
Prompt versionYes, with pruningYesGrows monotonically. Drop versions older than 90 days from the metric dimension set.
Tenant IDNoYesUnbounded growth. Derive per-tenant aggregates from traces or a separate rollup.
User ID, conversation ID, request IDNoYesUnbounded by definition
Chunk IDs, tool argumentsNoYesUnbounded and large

Per-tenant metrics without the explosion

Per-tenant cost and quality reporting is a legitimate requirement. Three approaches, in increasing order of effort:

  1. Tier bucketing. Replace tenant ID with tenant tier, typically five to ten values. Answers "are enterprise customers seeing worse latency" without per-tenant series.
  2. Top-N plus other. Emit the dimension only for the largest twenty tenants and bucket the rest as other. Covers most of the revenue with bounded cardinality.
  3. Separate rollup pipeline. Aggregate per-tenant figures from traces or from a billing event stream into a table, on a schedule. Correct, exact, and not in the metrics system at all. This is the right answer when per-tenant numbers are billed on.

Enforcement

Cardinality discipline fails by accident, usually when someone adds a dimension to debug something and leaves it. Enforce it in code rather than in review.

ALLOWED_METRIC_DIMENSIONS = frozenset({
    "gen_ai.operation.name", "gen_ai.request.model", "gen_ai.response.model",
    "gen_ai.provider.name", "error.type",
    "app.feature", "app.pipeline_version", "app.prompt_version",
    "app.tenant_tier",
})

def metric_attrs(**kwargs):
    rejected = set(kwargs) - ALLOWED_METRIC_DIMENSIONS
    if rejected:
        raise ValueError(
            f"High-cardinality dimensions rejected: {sorted(rejected)}. "
            f"Put these on the span instead."
        )
    return kwargs

Failing loudly in development is considerably cheaper than discovering the problem through a backend bill or an outage.

Section 13Instrumentation strategy

Three approaches, which are complementary rather than competing. Most production systems use all three.

ApproachMechanismCoversLimitation
Auto-instrumentationLibrary patching, typically one importProvider SDK calls, framework operationsKnows nothing about your pipeline stages or business context
Manual spansDecorators or context managers in your codeRetrieval, reranking, post-processing, agent stepsRequires discipline and review
ProxyRoute provider calls through a gatewayEvery model call regardless of language or frameworkNo visibility inside your application. Adds a hop.

Recommended combination

Auto-instrument the provider SDKs so that model calls are captured without effort, and add manual spans for your own pipeline stages. A proxy is worth adding when you have several services in several languages and need a single enforcement point for rate limits, key rotation or cost caps.

Vendor-neutral instrumentation built purely on OpenTelemetry, of which OpenLLMetry is the prominent example under Apache 2.0, keeps the instrumentation decision separate from the backend decision. That separation is worth something: Section 23 shows that with OTel-native instrumentation, changing backend is an operations-side configuration change rather than an application rewrite.

What to instrument manually

  1. Every pipeline stage that can fail independently or be skipped.
  2. Every point where a budget or threshold is enforced, recording whether it triggered.
  3. Every transformation of user input the user cannot see, such as query rewriting.
  4. Every degradation path, with app.degraded set.

The fourth is routinely missed and is the most common reason a wrong answer cannot be explained.

The generation wrapper

# telemetry/generation.py
import time
from contextlib import contextmanager
from opentelemetry import trace
from opentelemetry.trace import SpanKind, Status, StatusCode
from . import semconv as sc

tracer = trace.get_tracer(__name__)

@contextmanager
def generation_span(operation: str, provider: str, model: str, *,
                    temperature=None, max_tokens=None, metrics=None,
                    dimensions=None):
    name = f"{operation} {model}"            # low cardinality by construction
    dimensions = dimensions or {}
    started = time.perf_counter()

    # Sampling-relevant attributes set at creation.
    attrs = {
        sc.GEN_AI_OPERATION_NAME: operation,
        sc.GEN_AI_PROVIDER_NAME: provider,
        sc.GEN_AI_REQUEST_MODEL: model,
    }
    if temperature is not None:
        attrs[sc.GEN_AI_REQUEST_TEMP] = temperature
    if max_tokens is not None:
        attrs[sc.GEN_AI_REQUEST_MAX_TOK] = max_tokens

    with tracer.start_as_current_span(
        name, kind=SpanKind.CLIENT, attributes=attrs
    ) as span:
        result = _Result()
        try:
            yield result
        except Exception as exc:
            span.set_attribute(sc.ERROR_TYPE, type(exc).__qualname__)
            span.set_status(Status(StatusCode.ERROR))
            raise
        finally:
            elapsed = time.perf_counter() - started

            if result.response_model:
                span.set_attribute(sc.GEN_AI_RESPONSE_MODEL, result.response_model)
            if result.response_id:
                span.set_attribute(sc.GEN_AI_RESPONSE_ID, result.response_id)
            if result.finish_reasons:
                span.set_attribute(sc.GEN_AI_FINISH_REASONS, result.finish_reasons)
            if result.ttft is not None:
                span.set_attribute(sc.APP_TTFT, result.ttft)
                metrics["ttft"].record(result.ttft, dimensions)

            if result.input_tokens is not None:
                span.set_attribute(sc.GEN_AI_USAGE_INPUT, result.input_tokens)
                metrics["tokens"].record(
                    result.input_tokens, {**dimensions, "gen_ai.token.type": "input"})
            if result.output_tokens is not None:
                span.set_attribute(sc.GEN_AI_USAGE_OUTPUT, result.output_tokens)
                metrics["tokens"].record(
                    result.output_tokens, {**dimensions, "gen_ai.token.type": "output"})

            # Metrics are never sampled.
            metrics["duration"].record(elapsed, dimensions)

The two failure modes that matter

Ingest backpressure. When the write path slows, the queue grows. If the SDK blocks on export, your application latency now depends on your observability stack, which is an unacceptable coupling. Verify that your exporter drops rather than blocks, and alert on the drop counter.

Operational checklist

  • Retention enforced by automated lifecycle policy, not by a manual job somebody remembers.
  • Exporter drop counter monitored and alerted.
  • Backup and restore tested for the transactional store. Trace data is usually acceptable to lose; prompts, scores and annotations are not.

Why answered rate matters

A system can achieve excellent availability and latency while progressively refusing more questions, for instance because an ingestion job has been failing and the corpus is stale. Availability stays at 99.95%, latency improves because refusals are cheap, and the product is broken. Answered rate is the indicator that catches this, and it is almost never defined.

Error budget interpretation

Treat quality indicators as budgeted in the same way as availability. A grounding rate objective of 90% means a 10% budget. Consumption of that budget should gate changes to prompts, retrieval configuration and models, in the same way an availability budget gates deploys. Without that link, quality objectives are reported and not acted on.

  • Individual refusals. A refusal is usually correct behaviour.
  • Token count on a single request. Alert on the distribution.
  • Provider rate limits as pages. These are expected under load and should be handled by backoff. Page only if the retry budget is exhausted.

Section 19Online evaluation

Offline evaluation measures a fixed set of questions. Online evaluation measures what users actually asked. Both are necessary and they answer different questions.

The asynchronous scoring model

Scores are computed after the response is returned and written back against the trace. This is the architectural requirement that distinguishes LLM observability from general tracing, and it is why the backend must support writes to a completed trace.

Request ──▶ pipeline ──▶ response to user
                │
                └──▶ queue ──▶ evaluator ──▶ score written to trace ID
                                   │
                                   ├─ faithfulness
                                   ├─ answer relevance
                                   └─ policy compliance

The evaluation path MUST NOT be on the request critical path. It adds model calls, and a failure in the evaluator must not fail the user's request.

What to evaluate online, and at what rate

CheckRateCost per checkNotes
Faithfulness, is the answer supported by the context2 to 5%One judge callThe highest-value online check for RAG
Answer relevance2 to 5%One judge callCheap to compute alongside faithfulness
Policy compliance100% for regulated surfacesOne classifier callCan be a small model. Usually a hard requirement, not a sample.
PII leakage in output100%Pattern matching plus classifierCheap, and the failure is severe
Refusal correctness100% of refusalsOne judge callRefusals are low volume and a wrong refusal is invisible otherwise

Note the asymmetry. Quality checks are sampled because they are advisory. Safety checks are not sampled, because a single miss is a different kind of failure.

Judge reliability

Judge models disagree with human raters at a measurable rate, and the rate varies by dimension. Factual checks correlate better than subjective ones such as tone.

Two mitigations. Audit a sample of judgements against human review and track the agreement rate as its own metric. And use judge scores to detect movement rather than to certify absolute quality: a faithfulness score falling from 0.94 to 0.81 is a real signal even if neither figure is precisely correct.

Closing the loop to offline

Traces scored poorly online are the best available source of new offline evaluation cases. Build an explicit promotion path, with review, so that production failures become regression tests. Section 12 notes that promotion moves the data into a different retention and governance regime; make that boundary deliberate.

Section 21Cost attribution

Token usage is recorded by the standard metric. Turning that into a cost figure attributable to a feature, a tenant or a customer requires a small amount of deliberate work and is almost always asked for within the first quarter.

Computing cost

Do not compute cost in the SDK at request time. Prices change, negotiated rates differ from list, and caching discounts apply retrospectively. Record tokens and model; compute cost downstream from a price table with effective dates.

model_prices
  model                text
  provider             text
  input_per_1m_usd     numeric
  output_per_1m_usd    numeric
  cached_input_per_1m  numeric  nullable
  effective_from       date
  effective_to         date     nullable
  PRIMARY KEY (model, provider, effective_from)
SELECT
  s.attrs->>'app.tenant_id'        AS tenant,
  s.attrs->>'app.feature'          AS feature,
  date_trunc('day', s.start_time)  AS day,
  SUM( (s.attrs->>'gen_ai.usage.input_tokens')::bigint
       / 1e6 * p.input_per_1m_usd
     + (s.attrs->>'gen_ai.usage.output_tokens')::bigint
       / 1e6 * p.output_per_1m_usd ) AS cost_usd
FROM spans s
JOIN model_prices p
  ON p.model = s.attrs->>'gen_ai.response.model'
 AND s.start_time >= p.effective_from
 AND (p.effective_to IS NULL OR s.start_time < p.effective_to)
WHERE s.name LIKE 'chat %'
GROUP BY 1, 2, 3;
Join on gen_ai.response.model, not gen_ai.request.model. Providers alias and route. A request for a version-less model name can be served by any of several underlying versions at different prices, and billing against the requested name will not reconcile with the invoice.

The sampling problem

If cost is computed from sampled traces, it is wrong by the inverse of the sampling rate, and the error differs per class because the policy is tiered. Cost must come from unsampled metrics or from a dedicated billing event emitted on 100% of requests.

# Emitted on every request regardless of trace sampling.
billing_events.record({
    "ts": now,
    "tenant_id": tenant,
    "feature": feature,
    "provider": provider,
    "model": response_model,
    "input_tokens": usage.prompt_tokens,
    "output_tokens": usage.completion_tokens,
    "cached_input_tokens": usage.cached_tokens,
    "trace_id": trace_id,       # joinable, but not dependent on retention
})

Keeping the trace ID on the billing event lets you investigate an expensive request if the trace happened to be retained, without making the billing record depend on it.

Cost per resolved request, not cost per request. Section 22Debugging workflows

The telemetry exists to answer specific questions quickly. These are the workflows it should support, with the query path for each.

A user reports a wrong answer

  1. Obtain the trace ID. If your product does not surface it to support, add that before anything else in this section matters.
  2. Open the trace. Read the retrieval span attributes: what was app.retrieval.top_score, how many chunks were returned, which IDs.
  3. Join the chunk IDs back to the corpus. Was the correct passage among them?
  4. If yes, the failure is in reranking, context assembly or generation. Check whether the correct chunk survived to the generation span's context.
  5. If no, the failure is in retrieval or ingestion. Check whether the passage exists in the index at all.

Five steps, each answerable from the trace, with the branch at step 4 separating two entirely different investigations. A trace that does not record chunk IDs collapses this workflow into guesswork.

Cost rose without an obvious cause

  1. From billing events, identify which feature and model account for the increase.
  2. Compare the input token histogram against the previous period. A rightward shift means context growth.
  3. If context grew, check app.pipeline_version for a retrieval change, and app.retrieval.k for a configuration change.
  4. If output tokens grew instead, check app.prompt_version. A prompt change is the usual cause of more verbose answers.
  5. For agents, check the app.agent.steps_used distribution. A heavier tail means more runs looping.

Quality regressed after a deploy

  1. Group the grounding rate by app.prompt_version and app.pipeline_version. If the drop aligns with one version, you have your answer in a single query.
  2. If it does not align with a version, check whether a hosted model or reranker changed under you. Compare gen_ai.response.model distribution before and after.
  3. Check app.degraded rate. A dependency failing silently presents as a quality regression with no deploy to blame.
  4. Check retrieval top-score distribution. A fall indicates an index or corpus problem rather than a code change.

This is the workflow that justifies the app.prompt_version attribute. Without it, step 1 requires correlating deployment timestamps by hand and is frequently inconclusive.

Latency regression

  1. Compare p95 time to first token against p95 total duration. If only the total moved, generation is slower or longer, not the pipeline.
  2. Break span duration down by stage across the affected window. The guilty span is usually obvious.
  3. If reranking, check the degradation counter. A reranker that is slow but not yet timing out is the common case.
  4. If generation, check input token distribution. Longer context raises time to first token.

Section 23Backend migration

Platforms in this category are consolidating. Design so that changing backend is a configuration change rather than a project.

What determines migration cost

InstrumentationMigration cost
OTel-native, standard conventions, OTLP exportChange the exporter endpoint. An operations-side configuration change, with no application rewrite.
Vendor SDK with proprietary span modelReinstrument every call site. Weeks.

This is the strongest practical argument for emitting the standard conventions even while they carry Development status. The alternative is a bespoke schema that only one vendor understands.

What does not migrate

Telemetry is portable. These are not, and they are usually what makes a migration painful:

  • Historical traces. Most platforms offer no bulk export in a form another will ingest. Plan to run both in parallel for one retention period rather than migrating history.
  • Scores and annotations. Human review work is high-value and usually stored in a proprietary shape. Export it yourself on a schedule, into your own store, from day one.
  • Prompt versions. If prompts live in the observability platform, they are now coupled to it. Consider keeping prompts in version control with the platform as a mirror.
  • Dashboards and alerts. Always rebuilt. Keep their definitions in code so the rebuild is mechanical.

A dual-export period

# Export to both during migration. Verify parity, then remove the old one.
provider.add_span_processor(BatchSpanProcessor(OTLPSpanExporter(endpoint=OLD)))
provider.add_span_processor(BatchSpanProcessor(OTLPSpanExporter(endpoint=NEW)))

Run both for at least one full retention period. Compare trace counts, span counts per trace, and a sample of attribute values. Divergence usually indicates that one backend is silently dropping attributes it does not recognise, which is worth discovering before you decommission the old one.

Section 24Rollout

Instrument in an order that delivers value early and defers the expensive decisions until you have data to make them with.

PhaseScopeDelivers
1Auto-instrument provider SDKs. Standard metrics on 100% of requests. No content capture. No tracing backend beyond your existing one.Token cost, latency distribution, error rate. Usually answers the first three questions anyone asks.
2Manual spans for pipeline stages. Trace sampling at a flat 5%. Application attributes including prompt and pipeline version.Stage-level diagnosis. The ability to answer "which stage".
3Tiered content capture with redaction. Tail sampling with rule-based retention.Debuggability of specific failures at controlled cost and exposure.
4Feedback endpoint. Trace ID returned to the client. Implicit signals captured.Ground truth. The input to everything in phase 5.
5Online evaluation on a sample. Scores written back to traces. Quality SLIs defined.Quality as a monitored, budgeted property rather than an anecdote.

Sequencing notes

Phase 1 is a day of work and answers the cost question, which is usually what prompted the project. Do it first even if the rest is deferred.

Phase 4 before phase 5. Online evaluation without feedback gives you judge scores with nothing to validate them against. Feedback without evaluation still gives you a dataset of real failures, which is more useful than judge scores alone.

Do not begin at phase 3. Teams that enable full content capture before understanding their volume discover the storage cost and the compliance scope simultaneously, usually in the same meeting.

Section 25Conformance checklist

Conventions

  • Span names follow {operation} {model} and contain no high-cardinality values.
  • Span kind is CLIENT for provider calls, INTERNAL for in-process operations.
  • Error status is set only for failures. Refusals are not errors.
  • gen_ai.provider.name is set at span creation.
  • Convention version is pinned in configuration and recorded as a resource attribute.
  • Attribute names are centralised in one module.

Attributes and metrics

  • Request and response model both recorded, and cost joins on the response model.
  • Token usage recorded for input and output separately.
  • Finish reasons recorded, with truncation monitored.
  • Both standard histograms emitted with explicit bucket boundaries.
  • Metric dimensions enforced against an allow-list.
  • Prompt and pipeline version recorded on the root span.
  • Metrics emitted on 100% of requests, independent of trace sampling.

Content and privacy

  • Content capture is off by default and enabled per tier deliberately.
  • Redaction runs as a span processor before export.
  • Content tier recorded on the span.
  • Retention differentiated by tier, enforced by lifecycle policy.
  • Erasure path from a subject identifier to stored traces exists and has been tested.

Sampling and storage

  • Effective retention rate computed, not assumed from the headline rate.
  • 100% retention for errors, degradations, negative feedback and agent step-limit terminations.
  • Sampling decisions consistent across a trace.
  • Storage sized with content capture included in the arithmetic.
  • Exporter drops bounded and monitored.

Operations

  • Trace ID returned to the client and surfaced to support staff.
  • Feedback endpoint writes scores against trace IDs.
  • SLIs defined including answered rate and undegraded rate.
  • Alerts compare against the same hour last week, not the previous hour.
  • Online safety checks run on 100%; quality checks sampled.
  • Scores and annotations exported to your own store on a schedule.

Section 26Context propagation

Traces break at process and async boundaries unless context is propagated explicitly. LLM pipelines cross more of these boundaries than typical web services, because they fan out, queue work and call back.

Where context is lost

BoundaryFailureRemedy
Thread pool executorChild work starts with an empty context; spans become new rootsCapture and attach the context explicitly when submitting
asyncio.gatherUsually fine, because context vars propagate into tasks created from the current contextVerify. Tasks created outside the parent's context do not inherit it.
Message queueContext does not cross the brokerInject W3C traceparent into the message headers, extract on consume
Background evaluation workerThe scoring job is a separate trace entirelyDo not try to join it. Carry the trace ID as data and write the score against it.
Streaming responseThe span closes before the stream finishesKeep the span open until the stream completes, or record completion as a separate event
Retries at an outer layerEach attempt becomes a sibling with no indication they are the same logical operationRecord an attempt index attribute and keep attempts under one parent

Thread pools

from opentelemetry import context as otel_context

def submit_with_context(executor, fn, *args, **kwargs):
    ctx = otel_context.get_current()

    def _run():
        token = otel_context.attach(ctx)
        try:
            return fn(*args, **kwargs)
        finally:
            otel_context.detach(token)

    return executor.submit(_run)

Without this, a retrieval call dispatched to a thread pool produces an orphan trace containing one span, and your RAG trace shows a gap where retrieval should be.

Queue boundaries

from opentelemetry.propagate import inject, extract

# Producer
headers = {}
inject(headers)                      # writes traceparent, tracestate
queue.publish(topic, payload, headers=headers)

# Consumer
ctx = extract(message.headers)
with tracer.start_as_current_span("process_job", context=ctx,
                                  kind=SpanKind.CONSUMER):
    handle(message)

Use the standard W3C headers rather than a custom field. Every conforming tool understands traceparent, and a bespoke header means your traces join only inside your own code.

Streaming spans

A streaming generation produces its first token quickly and its last token much later. If the span closes when the request returns, the recorded duration measures the time to open the stream, not to complete it, and your latency metrics will be optimistic by an order of magnitude.

with generation_span("chat", "openai", model, ...) as gen:
    first_token_at = None
    chunks = []
    async for chunk in client.stream(messages=messages):
        if first_token_at is None:
            first_token_at = time.perf_counter()
            gen.ttft = first_token_at - started
        chunks.append(chunk)
    # Span closes here, after the stream is exhausted.
    gen.output_tokens = count_tokens(chunks)

Record both figures. Time to first token is the user-perceived latency; span duration is the resource cost. Treating either as the other produces wrong conclusions in opposite directions.

Linking rather than nesting

Some relationships are not parent-child. A follow-up turn in a conversation is a separate trace that relates to an earlier one. A batch evaluation run relates to many production traces. Span links express this without distorting the hierarchy.

link = trace.Link(previous_turn_span_context)
with tracer.start_as_current_span("rag.query", links=[link]) as span:
    ...

Nesting a conversation's turns under one root instead produces traces that grow without bound and never close, which breaks tail sampling, latency metrics and the user interface of most backends.

Section 27Measuring experiments

Prompt and pipeline changes are experiments whether or not they are run as such. Telemetry that carries version attributes turns a deployment into a measurement at no extra cost.

The minimum viable experiment

If every trace carries app.prompt_version and app.pipeline_version, a staged rollout is an A/B test. Group any metric by the version attribute and the comparison is available immediately.

SELECT
  attrs->>'app.prompt_version'                      AS variant,
  count(*)                                          AS n,
  avg((attrs->>'gen_ai.usage.output_tokens')::int)   AS mean_output_tokens,
  avg((attrs->>'app.context_utilisation')::float)    AS mean_utilisation,
  sum(CASE WHEN attrs->>'app.refused' = 'true'
           THEN 1 ELSE 0 END)::float / count(*)      AS refusal_rate
FROM spans
WHERE name LIKE 'chat %'
  AND start_time > now() - interval '7 days'
GROUP BY 1
ORDER BY 1;

Sample size

Quality differences between prompt variants are usually small, and small differences need large samples. For a binary outcome such as a thumbs-down rate, the approximate sample size per variant to detect an absolute difference d at 80% power and 95% confidence is:

n ≈ 16 × p(1 - p) / d²

Worked example. Baseline negative feedback rate p = 0.04. You want to detect an improvement to 0.03, so d = 0.01.

n ≈ 16 × 0.04 × 0.96 / 0.0001
  ≈ 16 × 0.0384 / 0.0001
  ≈ 6,144 per variant

At 400,000 requests per day split evenly, that is reached in under an hour of traffic. But negative feedback is left on only a small share of responses, so the effective sample is the feedback count, not the request count. At a 2% feedback rate, 6,144 feedback events requires roughly 307,000 requests per variant, which is a day and a half.

The common error is to declare a winner after 200 requests. At the volumes above, a difference that looks like a 30% improvement after an hour is well inside the noise. Compute the required sample before starting and do not look at the result before reaching it, because stopping early on a favourable reading is how teams ship regressions with confidence.

Metrics that need fewer samples

Continuous metrics with low variance reach significance far sooner than rare binary events. Prefer them for fast iteration:

MetricTypeTypical sample for a useful read
Output token countContinuous, low varianceHundreds
Context utilisationContinuousHundreds
Time to first tokenContinuous, right-skewedLow thousands
Judge-scored faithfulnessContinuous, moderate varianceLow thousands
Refusal rateBinary, moderate rateThousands
Negative feedback rateBinary, low rateTens of thousands of requests
Escalation rateBinary, very low rateHundreds of thousands

A practical sequence is to gate on the fast metrics first. If a new prompt increases output tokens by 40% with no change in utilisation, you have learned something useful in an hour and can reject it without waiting for feedback data.

Guardrail metrics

Every experiment should carry guardrails that stop it regardless of the primary metric:

  • Error rate, which must not rise.
  • p95 time to first token, which must not rise beyond a defined bound.
  • Cost per request, bounded.
  • Safety check failures, which must not rise at all.

Wire the guardrails to an automatic rollback. An experiment that improves answer quality while tripling cost is not a success, and discovering that at the end of a two-week test is avoidable.

Recording the experiment, not just the version

Where you run deliberate experiments rather than staged rollouts, record the assignment explicitly so that analysis does not depend on inferring cohorts from deployment timing.

span.set_attribute("app.experiment.id", "prompt-concision-v3")
span.set_attribute("app.experiment.variant", "treatment")
span.set_attribute("app.experiment.assignment_unit", "user")   # or session, tenant

The assignment unit matters. Assigning per request rather than per user means the same user sees both variants, which contaminates any metric measured at the session level and makes feedback uninterpretable.

Appendix CSampling configuration

An illustrative tail sampling policy for an OpenTelemetry collector. Rates follow Section 10; calibrate against your own volume using the arithmetic there.

processors:
  tail_sampling:
    decision_wait: 30s
    num_traces: 100000
    expected_new_traces_per_sec: 500
    policies:
      - name: errors
        type: status_code
        status_code: { status_codes: [ERROR] }

      - name: degraded
        type: boolean_attribute
        boolean_attribute: { key: app.degraded, value: true }

      - name: agent-step-limit
        type: string_attribute
        string_attribute:
          key: app.agent.terminated
          values: [max_steps, budget, error]

      - name: slow
        type: latency
        latency: { threshold_ms: 15000 }

      - name: expensive
        type: numeric_attribute
        numeric_attribute:
          key: app.cost_usd_micros
          min_value: 50000          # 0.05 USD

      - name: refusals
        type: and
        and:
          and_sub_policy:
            - type: boolean_attribute
              boolean_attribute: { key: app.refused, value: true }
            - type: probabilistic
              probabilistic: { sampling_percentage: 50 }

      - name: baseline
        type: probabilistic
        probabilistic: { sampling_percentage: 2 }

Negative feedback and retry signals arrive after the sampling decision window and cannot be expressed as tail sampling policies. Retain those traces by re-ingesting them from a buffer on receipt of the feedback event, or by holding a short-lived full-fidelity buffer separate from the collector.
